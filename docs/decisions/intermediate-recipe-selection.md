# 設計判断 ADR: 中間素材レシピ選択の管理単位

- **状態**: 採用（2026-11-19）
- **対象**: 製作リスト・BOM展開・素材集計
- **関連ユースケース**: [UC-001〜UC-004](../product-requirements.md)

## 背景とユーザーの事情

利用者は中間素材を自分で製作することがある。同じ中間素材でも複数レシピが存在し、使う素材が異なることがある。また、利用者によって製作可能なレシピは異なり、「レシピ1でしか製作できない」といった場合もある。したがって固定レシピで算出した素材一覧では、利用者の実態を表せない。

一方、単一完成品のBOMの複数枝に同一中間素材が現れる場合、各枝ごとに異なるレシピを指定できるようにすると、状態・操作・数量計算の複雑さが増す。

## 決定

- 中間素材に複数レシピがあれば、利用者がレシピを選択できる。
- 選択状態は **登録製品recipeId × 中間素材itemId** 単位とする。
- 同じ登録製品内の同一中間素材が複数の枝に現れても、選択は共有する。
- 別の登録製品（別recipeId）では、同一中間素材に別のレシピを指定できる。
- 初期選択は候補の最小recipeId。変更したら該当完成品のBOMと全体の必要素材集計を再計算する。
- **レシピ選択を共有しても数量は経路別に算定する**。同一中間素材を先に合算して製作回数を最適化しない。

## 採用理由

1. ユーザー自身が製作可能な方法に対応し、必要素材がレシピごとに変化するケースを扱える。
2. 同一製品内での選択の一貫性を保ち、同じ素材の枝ごとに何度も設定する負担を減らせる。
3. 状態を `(recipeId, itemId) -> selectedRecipeId` として単純に表せる。
4. 登録製品間の選択独立性を維持でき、既存の製品別BOM展開・集計方針と整合する。

## 検討した代替案と見送った理由

- **全登録製品でitemIdごとに選択を共有**: 同じ中間素材でも完成品ごとに製作方法を変えたい場合に対応できないため不採用。
- **同一製品内でもBOMノード／経路ごとに選択**: 最大限の自由度があるが、初期段階では操作とノード識別・選択状態管理のコストが大きいため見送り。
- **選択不可・最小recipeIdに固定**: 利用者が製作できないレシピを選ぶ可能性があるため不採用。
- **所有ジョブや習得状況から自動選択**: 認証・習得データの取得を要するため現時点のスコープ外。

## 影響範囲

- UI: 完成品の詳細で中間素材のレシピを選択できるようにする。選択は同一完成品内の同一中間素材の全表示に一貫して反映する。
- 状態管理: 登録製品recipeIdを外側のキーとし、その製品内でitemIdごとの選択recipeIdを保持する。
- 計算: 下位BOMの再展開・数量更新を行う。各出現経路ごとの切り上げはそのまま維持する。
- テスト: 同一製品内の選択共有、異なる製品での選択独立、選択変更後の再計算、経路別切り上げを確認する。

## 将来の見直し条件

実際のユーザーから「同一完成品内で同じ中間素材を枝ごとに異なるレシピで作りたい」という利用例が確認された場合、選択キーをBOMノード・経路単位へ拡張することを再検討する。現時点で必要性が確認されていないため機能要件には含めない。

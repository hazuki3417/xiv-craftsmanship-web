# 設計判断 ADR: 製作品の操作は即時反映・フロントエンド状態管理とする

- **状態**: 採用（2026-11-19）
- **対象**: 製品検索・レシピ選択・BOM表示・数量入力・製作リスト
- **関連ユースケース**: [UC-005〜UC-009](../product-requirements.md)

## 背景 / 利用者の操作

利用者はまず製品名を検索Inputへ入力し、候補から製作レシピを選ぶ。これにより製品が選択状態となり、そのBOMツリーが表示される。別に完成品の数量を指定するInputがあり、選択中の数量を変更すると、その数量に連動してツリーや必要素材の表示が更新される。利用者が製作リストへ追加するのは、検索候補を選択することとは別の操作である。

この製作計画はログイン不要の参照・試算用途であり、個人の選択状況やリストをバックエンドへ永続化する要求はない。

## 決定

1. 検索結果からレシピを選択すると、レシピが現在の選択状態となりBOMツリーを表示する。これだけではリスト登録しない。
2. 完成品数量は専用Inputで変更可能とする。**有効な変更の確定時点で、保存ボタンなしにBOM数量と表示を更新する**。
3. 登録済み製品の詳細を編集する場合も同様に、対象製品の数量と集計を即時反映する。ただし検索・プレビュー中の未登録レシピが登録済み製品を暗黙に上書きしないこと。
4. 製作リストへの追加・削除、中間素材の選択レシピ、現在の選択・数量・全体集計など、利用者固有の作業状態は**フロントエンドが所有**する。
5. バックエンドは製品・レシピ・BOMの読み取りAPIを担う。**利用者の選択状態や製作リストのための保存API・DBテーブル・アカウントは用意しない**。
6. **ブラウザ・タブを閉じても製作リストと選択状態を保持し、同じブラウザでの再訪時に復元する**（2026-11-19の追加決定）。保存先はブラウザ内の永続ストレージとし、`localStorage`等を候補にする。
7. ブラウザに保存する対象は登録製品のrecipeId・必要数量・中間素材ごとの選択recipeIdと、現在の選択レシピ・数量などの利用者操作状態。参照元BOMデータの正本は引き続きバックエンドにあり、復元時は再取得・再計算する。
8. 別端末・別ブラウザとの自動同期は対象外。ブラウザの保存データ消去・ストレージ利用不可などの場合は復元保証しない。

## 根拠

- 検索・選択からBOM表示、数量変更による再計算までが1つのインタラクティブな操作として連続している。
- 利用者に毎回「保存」を求めると、画面上の数量と集計結果の反映タイミングが直感的でなくなる。
- 個人の製作計画は参照データそのものの更新ではないため、読み取りAPIとクライアントの編集状態を分離できる。
- サーバー状態・認証・サーバー永続化機構・同期APIを追加せず、今回の規模と目的に即した実装にできる。
- ブラウザの終了だけで作業中の製作計画が失われると、複数製品を登録して準備する利用者が再入力を強いられるため、ローカルでの継続利用を優先する。

## 比較した代替案

- **明示的な保存ボタンを採用する**: 変更の取り消しは容易だが、選択と数量変更に連動してツリーを更新する現行の操作フローと合わないため不採用。
- **バックエンドに製作リストを保存する**: 端末間共有や履歴を可能にできるが、アカウント・永続化・同期を伴い、現要件では過剰なため不採用。
- **選択時に自動的に製作リストへ登録する**: BOMの試算だけしたい場合まで登録されるため不採用。
- **フロントエンド内での永続保持を一切行わない**: 既存のReact stateのみの方式は簡単だが、ブラウザ終了後の継続利用ができないため不採用。
- **sessionStorageのみで保持**: 同じタブの再読み込みには対応できてもタブ終了後の継続利用を保証できないため不採用。
- **ブラウザ内永続ストレージ（localStorage等）を利用する**: サーバー保存なしで同一ブラウザの継続利用を可能にするため採用。容量制限・形式変更・ストレージ削除への対応は別途設計する。

## 現行実装との照合結果（2026-11-19時点の静的調査）

- `RecipeSearch.tsx`: 検索Inputをdebounceし、`getCraft` で候補取得、候補選択時に `getRecipe` を取得し `RecipeProvider` のレシピ/BOM状態へ反映。
- `QuanitityChangeInput.tsx` → `useQuantity.ts` → `RecipeProvider.tsx`: 完成品の数量Inputからstateを変更し、`useEffect` が `setQuantity` へ連動。数量は現行reducerで1〜999に制限（これを確定仕様とするかは別論点）。
- `Craft.tsx`: 製作リストへの追加は独立のボタン操作。リスト表示のstateは `MaterialManagerProvider.tsx` の `useState` が保持し、追加・削除・集計はフロントで処理する。
- **要実装/要確認**: `CraftItemSelect.tsx` の選択値は内部stateで管理され、選択から登録済み製品を `RecipeProvider` にロードする連携は見当たらない。登録済み製品の数量編集を即時反映する要求は、コード上で一通り実装済みとは確認できない。
- **要確認**: `app/page.tsx` の条件付きsegment表示によってProviderが再マウントされる場合、製作リストの状態が失われ得る。再読み込み・画面切替をまたいで保持する要求が確定したため、実装との差分として確認する。
- 既存のコメントに「バックエンドで集約」とある箇所は実際のfrontend処理と齟齬があるため、実装修正時に整理する。

ここに記すのは**要求とコードの照合**であり、動作テストを実施したという意味ではない。

## 再検討する条件

端末間共有、ログイン後の製作計画保存、複数人での共同管理、過去の計画の再利用が重要なユースケースとして確認された場合に限り、バックエンド永続化の導入を再検討する。

保存形式・旧データの移行または破棄・参照レシピの変更時の復元・明示的なクリア手段、および入力途中の値の扱いは、次の要求整理で個別に決定する。
